# 스펙과 테스트로 일하기

역할이 없어도 쓴다. 기능을 만들거나 동작을 바꾸는 작업을 시작할 때, 작업을 넘겨받았을 때, 끝났다고 보고하기 전에 읽는다. 누가 스펙을 승인하고 언제 완료로 보는지는 프로젝트 규칙과 역할 지침이 정한다.

## 스펙이 있는 곳

| 프로젝트 | 스펙 | 작업 단위 |
|---|---|---|
| `openspec/`가 있다 (`orai.toml`에 `[integrations.openspec]`) | `openspec/specs/<기능>/spec.md`의 요구와 시나리오 | `openspec/changes/<변경>/`의 변경 하나 (proposal, specs 델타, design, tasks) |
| 없다 | 프로젝트 규칙(AGENTS.md)이 정한 곳 | 프로젝트 규칙이 정한 단위 |

- 스펙은 shelf로 찾고 원문을 파일로 읽는다. 진행 중인 변경은 `openspec list`와 `openspec status --change <변경>`으로 본다.
- OpenSpec의 단계는 OpenSpec 스킬이 안내한다: 탐색 `openspec-explore`, 변경 제안 `openspec-propose`, 구현 `openspec-apply-change`, 본 스펙에 합치기 `openspec-archive-change`.
- OpenSpec 스킬 폴더(`.agents/skills/openspec-*`)는 고치지 않는다. `openspec update`가 통째로 다시 쓴다. 프로젝트의 규칙은 `openspec/config.yaml`의 `context`, `rules`, `operations`에 둔다.

## 순서

1. **기준 확인**: 이번 작업이 만족시킬 시나리오를 정한다. 시나리오가 없거나 모호하면 구현하지 않고 스펙부터 고치거나 질문한다.
2. **실패 테스트 먼저**: 시나리오마다 그것을 확인하는 테스트를 쓰고, 실행해서 실패하는 것을 본다. 실패를 보지 못한 테스트는 시나리오를 확인한다는 근거가 아니다. 테스트 이름이나 주석에 시나리오 이름을 남긴다.
3. **최소 구현**: 그 테스트가 통과할 만큼만 구현한다. 통과한 뒤에 정리한다.
4. **전체 검사**: 프로젝트의 전체 검사 명령(AGENTS.md나 `mise tasks`에 있다)을 실행한다.
5. **스펙과 맞추기**: 구현하면서 스펙과 다르게 해야 했다면 스펙(OpenSpec은 변경의 델타와 tasks)을 먼저 고친다. 코드와 스펙이 다른 채로 끝내지 않는다.
6. **보고**: 아래 형식으로 보고한다.

작은 버그 수정은 스펙 없이 해도 된다. 그때도 재현하는 테스트를 먼저 쓴다.

## 보고 형식

| 항목 | 내용 |
|---|---|
| 대상 | 커밋, 변경 이름(OpenSpec) |
| 시나리오별 검증 | 시나리오 → 테스트 이름 → 종류(fixture·fake, 실제 동작) → 결과 |
| 실행한 명령 | 전체 검사 명령과 결과 |
| 검증하지 못한 범위 | 실행하지 않은 시나리오와 그 이유 |

- fixture·fake 통과와 실제 동작을 섞어 쓰지 않는다. 실행하지 않은 것은 "미검증"으로 적는다.
- 실패한 검사를 성공으로 적지 않는다. 테스트를 건너뛰거나 지워서 통과시키지 않는다.

## 역할 사이에서

- 작업을 맡길 때: `todo` 메시지 본문에 변경 이름(또는 스펙 경로)과 이번에 만족시킬 시나리오만 적는다. 스펙 내용을 메시지에 옮겨 쓰지 않는다.
- 기준이 모호할 때: 구현 전에 `question`으로 묻는다.
- 끝났을 때: 받은 메시지에 `reply`로 위 보고 형식을 보낸다. 메시지 명령은 [../SKILL.md](../SKILL.md)에 있다.
